# Security

## Turn the login on first

Right after installation the UI and API are open to anyone who can reach them. While the login is off, anyone who opens the UI can replace or delete the bot token, change receivers and send messages as the bot. No API request returns the token or the password themselves.

Without login, open the UI only through `kubectl port-forward` or a proxy with authentication.

## How the login works

- One shared user name and password from `KAMERTON_AUTH_USER` and `KAMERTON_AUTH_PASSWORD`. In Kubernetes they come from a Secret (`auth.existingSecret`, keys `username`, `password` and optionally `session-secret`) and never go into a ConfigMap or an annotation. Locally they come from a `.env` file.
- Setting only one of the two is a startup error.
- With login on, every `/api/*` request needs a session except `/healthz`, `/api/v1/health` and `/api/auth/*`.
- The session is an HttpOnly cookie signed with HMAC-SHA256, valid for 12 hours. The signing key is `KAMERTON_AUTH_SECRET` (Secret key `session-secret`) or, without it, a key derived from the password, so changing the password ends all sessions.
- Five failed logins per minute from one address lock that address for the rest of the minute (429).

```sh
kubectl -n kamerton create secret generic kamerton-auth \
  --from-literal=username=admin --from-literal=password='<strong password>'
helm upgrade kamerton ./deploy/helm/kamerton -n kamerton --reset-then-reuse-values \
  --set auth.existingSecret=kamerton-auth
```

## The X-Requested-With header

State-changing requests must carry an `X-Requested-With` header. The UI sends it. A browser will not send such a header from another site without permission, so it blocks cross-site request forgery. If you call the API from your own scripts, add the header to state-changing requests.

## HTTPS

Without HTTPS the password travels in clear text. Terminate TLS at the ingress. The session cookie is marked Secure when the ingress sets `X-Forwarded-Proto: https`.

## Where secrets live

Secrets never go into the system description, the chart values or the repository.

| What | Where |
| --- | --- |
| Telegram bot token | Secret `kamerton-telegram`, key `bot-token`, in Kamerton's namespace |
| SMTP password | Secret `kamerton-smtp`, key `password` |
| Login user name and password | The Secret from `auth.existingSecret`, or one created by the chart |
| Grafana admin password | Secret `kamerton-grafana`, generated by the Grafana chart |
| Webhook token for Alertmanager | Secret `kamerton-webhook`, key `token`, generated by the core |

ConfigMaps hold nothing secret: `kamerton-telegram-state` (bot name, chats, polling state), `kamerton-email-state` (server, sender, login), `kamerton-stacks` (addresses and labels of the sets of programs), `kamerton-followup-state` (which incidents already got a follow-up), `kamerton-incident-history` and `kamerton-noise-state` (see [What is kept about incidents](#what-is-kept-about-incidents)).

The token is sent only to Telegram's Bot API. Transport errors that embed the request URL with the token are scrubbed before they reach logs or responses. The core reads the token Secret with direct GETs; RBAC grants get/update/patch/delete on that one Secret by name plus `create` on Secrets in the namespace (Kubernetes cannot restrict `create` by name), and no list or watch.

## Incidents

### The webhook

`POST /api/v1/hooks/alertmanager` is called by Alertmanager, not by a browser, so it needs no login session and no `X-Requested-With` header. It requires `Authorization: Bearer <token>`. The token is 256 random bits that the core generates into the Secret `kamerton-webhook` in its own namespace, and it is compared in constant time. The generated AlertmanagerConfig references that Secret.

The endpoint only starts the follow-up message and never changes settings. Someone with the token can make Kamerton send messages to the system's own chats and addresses, at most one per incident. Turn it off with `incidents.followUp.enabled=false`.

### Read access for the evidence

To say what changed in the workload, the core reads pods, events, ReplicaSets and StatefulSets in all namespaces: get and list, read-only, no Secrets. Turn it off with `incidents.followUp.workloadRead=false`; the follow-up then has no "what changed" part.

A quoted log line is shortened but not scrubbed. Whatever the service writes to its log may appear in the chat and in the incident history.

### What is kept about incidents

- `kamerton-incident-history`: service and alert names, times, the follow-up's evidence including the log line, the notes people write, and for the "incident over" messages the IDs of the chats and messages, so that replies can be matched. No names or user IDs of people. At most 300 incidents of the last 180 days.
- `kamerton-noise-state`: counters of "useful" and "noise" per rule, nothing about who pressed.
- `kamerton-followup-state`: which incidents already got a follow-up, for a day.

The bot reads the text of a message only when it replies to an "incident over" message and comes from a chat that gets the system's alerts. Other messages only reveal chats, as before. A note is stored as written and escaped wherever it is shown.

## Auto-instrumentation

`autoInstrument.enabled` is off by default. When on, it installs OpenTelemetry eBPF Instrumentation as a DaemonSet in Kamerton's namespace. By default each pod is a **privileged container** with `hostPID: true`: all capabilities, host devices, no AppArmor or seccomp confinement. No host paths and no host network. Kamerton's namespace must admit privileged pods (Pod Security level `privileged`) while it is on.

On a k3s cluster with AppArmor on, the agent with only the capabilities OBI's documentation lists (`BPF`, `PERFMON`, `SYS_PTRACE`, `DAC_READ_SEARCH`, `CHECKPOINT_RESTORE`, `NET_RAW`) could not enter pods' network namespaces and recorded nothing. Privileged, it worked. With `opentelemetry-ebpf-instrumentation.privileged=false` it runs as UID 0 with hostPID, those capabilities plus `SYS_ADMIN`, and a read-only root filesystem. That mode follows from the documentation and source and has not been tried. `SYS_ADMIN` is close to root.

Either way this is node-level access. The agent can load eBPF programs, read every process's executable and `/proc` entries, and see request metadata (method, path, status, peer addresses) of HTTP, gRPC, SQL and other calls on the node, including TLS traffic of Go and OpenSSL programs. It does not write trace headers into application traffic, and Java agent and Node.js injection are off.

It exports only traces, to Kamerton's Collector, which stores them in Tempo. Spans carry URL query strings, with values of known sensitive keys replaced by `REDACTED`; no SQL text or bodies by default. Its ClusterRole reads pods, services, nodes and ReplicaSets in all namespaces.

## Secret references

Alertmanager sends the value of a Secret a receiver references to that receiver's endpoint: the SMTP password goes to the `smarthost`. If a description could reference any Secret, it could be used to send someone else's secret to a server of your choosing. So a description saved through the API or the UI may reference a Secret only when:

1. a Telegram receiver names Kamerton's own token Secret, in Kamerton's namespace;
2. an email receiver names Kamerton's own SMTP Secret together with the mail server and login configured in Kamerton (another `smarthost` is refused);
3. the stored version of the same system already had that exact reference (for email: with the same `smarthost` and login). This keeps descriptions applied with kubectl by a cluster admin editable in the UI.

Anything else is refused with 400 `secret_not_allowed`; validation and preview report the same error. The API creates descriptions only in Kamerton's namespace (or the single watched one), otherwise 400 `namespace_not_allowed`. `runbookURL` and `--external-url` must be absolute http(s) URLs.

## What the login does not do

- One shared user: no roles and no per-user audit.
- The login rate limit is kept in memory per replica and counts the TCP peer address, so behind an ingress all clients share it.
- Notes on incidents and "useful" or "noise" verdicts are not tied to a person. With one shared user there is no way to tell who wrote what.
