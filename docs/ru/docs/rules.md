# Библиотека правил

Kamerton создаёт правила оповещений Prometheus по описанию системы. Каждый файл правил проверяется парсером самого Prometheus, прежде чем покинуть генератор. Prometheus проверяет правила каждые 15 секунд; правило срабатывает, когда условие держится дольше заданного времени (`for`).

## Общее для всех правил

Важность по умолчанию «критично» для важных сервисов (`critical: true`) и «предупреждение» для остальных. У каждого правила её можно задать явно: `severity: critical` или `severity: warning`.

Правила ошибок не срабатывают на одной ошибке в тихом сервисе, им нужен минимальный поток запросов. Правилам задержки достаточно 3 запросов за окно, поэтому редкие операции (два заказа в минуту) тоже проверяются.

Любое правило выключается переключателем в списке правил или полем в описании; поля указаны ниже. У каждого правила может быть [свой текст оповещения](./notifications#свои-тексты). В карточке правила видно, сколько раз оно сработало бы на данных Prometheus за день, 3 или 7 дней.

Значения по умолчанию ниже — те, что действуют, если ни `defaults`, ни сервис их не задали.

## Запросы

### Ошибки

`KamertonErrorRateHigh`. Доля запросов, завершившихся ошибкой, выше порога.

| | |
| --- | --- |
| По умолчанию | порог 5% (`threshold: 0.05`), не меньше 0,05 запроса в секунду, держится 1 мин |
| Поля | `errorRate.threshold`, `minRequestsPerSecond`, `for`, `severity` |
| Выключить | `errorRate.enabled: false` |

### Ошибки в каждой операции

`KamertonOperationErrorRateHigh`. То же, но отдельно по каждой операции сервиса, чтобы сбой одной редкой операции не тонул в здоровом потоке остальных. Нужно хотя бы 3 ошибки операции за окно. Включено по умолчанию.

Выключить: `errorRate.perOperation: false`. Операции со своими порогами (`operations`) проверяются своим правилом.

### Медленные ответы

`KamertonLatencyHigh`. Квантиль времени ответа выше порога, хотя бы 3 запроса за окно.

| | |
| --- | --- |
| По умолчанию | квантиль 0,95, порог 1000 мс, держится 2 мин |
| Поля | `latency.quantile`, `thresholdMs`, `for`, `severity` |
| Выключить | `latency.enabled: false` |

### Медленные ответы в каждой операции

`KamertonOperationLatencyHigh`. Квантиль операции выше порога (хотя бы 3 запроса) — для операций, которые за прошлый час укладывались в порог. Держится 30 секунд. Включено по умолчанию.

Выключить: `latency.perOperation: false`.

### Замедление относительно обычного

`KamertonLatencyAboveNormal`. Квантиль сервиса в 5 раз больше, чем за прошлый час (закончившийся 10 минут назад), и больше 100 мс. Держится 1 минуту. Порог от команды не нужен: так видно, например, отказавший кэш, после которого ответы выросли с 7 до 300 мс.

Множитель: `latency.aboveNormalFactor`. Выключить: `latency.aboveNormalFactor: 0`.

### Запросы перестали поступать

`KamertonRequestsStopped`. Сервис, до которого никто не может достучаться, не пишет ошибок — к нему просто перестают приходить запросы. Правило сравнивает текущий поток входящих запросов с обычным: средним за последние сутки, по тем отрезкам, где данные были.

| | |
| --- | --- |
| Срабатывает | поток не больше 10% обычного (`threshold: 0.1`), обычный поток больше 0,02 запроса в секунду (около одного в минуту), держится 2 мин |
| Молчит | пока истории меньше часа; пока данных нет у большинства сервисов системы сразу — тогда остановилась доставка телеметрии, а не сервис |
| По умолчанию | включено для важных сервисов типа `http` и `grpc`; у очередей и баз данных — только если задано у сервиса |
| Поля | `trafficDrop.enabled`, `threshold`, `minRequestsPerSecond`, `for`, `severity` |

## Ресурсы подов

### Память и процессор выше порога

`KamertonMemoryHigh`, `KamertonCPUHigh`. Работают, когда порог задан явно: `saturation.memory` (например, `512Mi`) или `saturation.cpuCores` (например, `0.5`). Держатся 2 минуты по умолчанию. Явный порог заменяет правила «у лимита» и «выше обычного» ниже.

### Перезапуски

`KamertonPodRestarting`. Контейнер перезапускается чаще, чем `saturation.maxRestartsPerHour` раз в час (по умолчанию 3).

Выключить: `saturation.restartsEnabled: false`.

### Память у лимита

`KamertonMemoryNearLimit`. Порог памяти не задан: память пода больше 95% его лимита, и по тренду за час она дойдёт до лимита за 30 минут. Лимит должен быть у всех контейнеров пода.

Доля: `saturation.memoryLimitShare`. Выключить: `saturation.memoryLimitShare: 0`.

### Процессор у лимита

`KamertonCPUNearLimit`. Порог процессора не задан: больше 90% лимита CPU пода.

Доля: `saturation.cpuLimitShare`. Выключить: `saturation.cpuLimitShare: 0`.

### Процессор выше обычного

`KamertonCPUAboveNormal`. Порог процессора не задан: под использует больше 0,5 ядра и в 3 раза больше обычного (среднее за прошлый час, закончившийся 10 минут назад). Подходит для подов без лимита CPU.

Множитель: `saturation.cpuAboveNormalFactor`. Выключить: `saturation.cpuAboveNormalFactor: 0`.

### Нехватка памяти (OOMKilled)

`KamertonOOMKilled`. Последнее завершение контейнера — OOMKilled, и он перезапустился за последние 10 минут. Срабатывает сразу.

Выключить: `saturation.oomKilledEnabled: false`.

Все правила ресурсов выключаются вместе полем `saturation.enabled: false`.

## Очереди

### Отставание очереди

`KamertonQueueLagHigh`. Для сервисов типа `queue`: в топике копятся необработанные сообщения, отставание группы потребителей больше `queue.maxLag`. Держится 2 минуты по умолчанию.

### Очередь перестали читать

`KamertonQueueConsumerStopped`. В группе потребителей топика нет участников 1 минуту, или отставание больше нуля держится 3 минуты, а смещение группы не двигается. Срабатывает при любой нагрузке, порог не нужен. Держится 1 минуту, важность как у правила отставания. Включено по умолчанию.

Выключить: `queue.consumerStoppedEnabled: false`. Метрики: `telemetry.queues.membersMetric` и `offsetMetric`.

## Цель доступности (SLO)

`KamertonSLOBurnRateFast`, `KamertonSLOBurnRateSlow`. Запас допустимых ошибок тратится слишком быстро. Схема с несколькими окнами и несколькими скоростями расхода — по книге Google SRE Workbook; множители выводятся из окна SLO.

```yaml
slo:
  objective: 99.5   # доля успешных запросов, %
  window: 30d       # по умолчанию 30d
```

Правило создаётся, только если у сервиса задан `slo`.

## Свои правила

Любое условие на любую метрику Prometheus: из частей (метрика, функция, агрегация, сравнение) или выражением PromQL. Создаются на вкладке «Правила» или в поле `customRules` сервиса. См. [Описание системы](./describe-system#свои-правила).

## Правила с «обычным»

Правила, которые сравнивают сервис с его обычным поведением, молчат, пока истории недостаточно: новый сервис, первый час после пропуска данных.
